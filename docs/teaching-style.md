# 非技术学习者教学风格指南

## 核心原则

让学习者先看懂问题，再看见结果，最后知道这个方法叫什么。

课程的每一节都要回答三个问题：

1. 这能帮我解决什么问题？
2. 我现在能不能跟着做出来？
3. 我怎么知道自己做对了？

## 概念讲解的两种方式

### 生活故事法

适用于上下文、Agent、任务拆解、权限、记忆、工作流和多 Agent 等抽象概念。

讲解顺序：

1. 讲一个学习者熟悉的生活场景。
2. 让场景里出现一个需要解决的冲突。
3. 通过人物的选择展示概念如何工作。
4. 在故事结尾揭示正式名称。
5. 对照解释每个隐喻对应的真实概念。
6. 立刻安排一个与学员工作相关的练习。

例如，解释 Agent 时，可以先讲一个项目经理如何把一项工作交给助理：说明目标、交付时间、资料位置、做事边界和检查方法。故事结束后再说明，这个“助理”就是 Agent，这些交代分别对应目标、上下文、权限和验收标准。

### ELI5 视觉法

适用于一个图就能解释清楚的关系，例如：

- AI 如何读取项目资料
- 一个任务如何被拆成几个步骤
- 多个 Agent 如何分工
- 一个工作流如何从输入走到输出

使用 `$eli5` 或 `/eli5 <主题>` 生成大图少字的 HTML 解释，再配合实际练习。图中只保留核心关系，不把所有术语和细节塞进去。

### 大白话问题分析法

遇到复杂问题时，可以借用毛泽东思想中适合问题分析的几个方法，把技术问题翻译成普通人能行动的语言：

- **抓主要矛盾**：先找出现在最影响结果的一个问题，不同时处理所有问题。
- **具体问题具体分析**：不套用万能提示词，先看目标、资料、限制和当前条件。
- **从实践中来，再回到实践中去**：先做一个最小尝试，根据结果修正方法，再回到真实工作中验证。
- **分清主次和先后**：先解决能让项目继续推进的关键步骤，再处理优化和高级功能。
- **通过现象看本质**：报错只是表面现象，要追问实际卡在哪里，是资料不全、目标不清、权限不足还是验收标准缺失。

使用这类方法时，语言要直接、具体、可执行。不要把理论名称当作结论，而要把它变成下一步行动。例如：

> 现在项目做不出来，先别急着换模型。先看最主要的问题：AI 是不知道要做什么，还是没有做事所需的资料？把这两个问题分开，先补资料，再重新交代任务。

这类解释方法用于帮助学习者建立判断顺序，最后必须回到一次实际操作和结果检查。

## 项目实践方法：从结果倒推最小可行路径

项目实践可以借用马斯克经常使用的工程思维，重点不是模仿某个人的表达，而是训练学习者从真实结果出发：

1. **先问最终要解决什么问题**：不从“我要学哪个功能”开始，而从“我要让什么工作变得更快、更准或更容易完成”开始。
2. **拆出必要条件**：确认完成结果真正需要哪些资料、步骤、工具和判断。
3. **删掉不必要的步骤**：任何流程、字段、功能和规则都要说明存在理由。
4. **先做最小版本**：先完成一个能运行、能检查的版本，再增加功能。
5. **快速验证和修正**：用真实输入测试，记录哪里失败，优先修正最影响结果的问题。
6. **最后再自动化**：只有当手动流程已经清楚、稳定并值得重复时，才把它交给 Agent 或自动化工具。

课程中的项目不以功能数量作为进度，而以是否产生可验证结果作为进度。每个项目都要写清楚：目标结果、最小版本、验收方式、失败记录和下一步改进。

## 禁用的讲法

- 连续出现多个没有解释的缩写。
- 先讲命令、参数和配置文件，再说明它们解决什么问题。
- 用“上下文窗口”“自治循环”“编排”等词替代具体场景。
- 用看似完整的概念清单代替一次真实操作。
- 只展示成功案例，不讲失败、检查和修正。

## 每节课的验收

学习者不需要复述定义，但必须能够：

- 用自己的话说明它解决的问题。
- 在自己的项目中完成一次操作。
- 发现结果不对时指出问题所在。
- 根据验收标准要求 AI 修正结果。
